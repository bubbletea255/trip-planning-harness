# 공용 하네스 템플릿 체크리스트

이 문서는 여행 계획 하네스 v3.2를 만들며 얻은 구조를 다음 하네스에 재사용하기 위한 설계 카드이자 체크리스트다.

목적은 매번 LLM과 처음부터 구조를 다시 토론하지 않고, 이 문서를 먼저 읽힌 뒤 같은 원칙으로 새 하네스를 설계하게 만드는 것이다.

---

## 1. 이 템플릿의 목표

이 템플릿은 다음 상황에서 사용한다.

- 반복 업무를 AI에게 맡기고 싶다.
- 중간 산출물과 최종 산출물을 파일로 남기고 싶다.
- Claude Code와 Codex 중 선택해서 같은 하네스를 실행하고 싶다.
- 두 모델의 결과를 비교하고 교차검증하고 싶다.
- 나중에 더 복잡한 하네스, 예를 들어 가치투자 21단계 하네스를 만들 때 같은 구조를 재사용하고 싶다.

핵심 원칙:

> 업무 의미는 `harness/`에 두고, 플랫폼별 실행 방식은 얇은 adapter로 둔다.

---

## 2. 이 구조가 해결하려는 문제

나쁜 구조는 같은 업무 규칙을 여러 곳에 복사한다.

```text
agents/researcher.md
.claude/agents/researcher.md
.agents/skills/researcher/SKILL.md
```

이렇게 되면 시간이 지나면서 규칙이 조금씩 달라진다.

- Claude와 Codex 결과가 다른 이유가 모델 차이인지 지침 차이인지 알기 어렵다.
- 같은 규칙을 여러 파일에서 고쳐야 한다.
- 한쪽만 최신화되어 drift가 생긴다.
- 교차검증과 A/B 테스트가 흐려진다.

그래서 이 템플릿은 공통 원장과 플랫폼 adapter를 분리한다.

## 3. 권장 폴더 구조

```text
{harness-project}/
├── AGENTS.md                     # Codex와 공통 프로젝트 안내
├── CLAUDE.md                     # Claude Code 프로젝트 안내
│
├── harness/                      # 공통 업무 원장
│   ├── ORCHESTRATOR.md           # 전체 실행 흐름, Phase, 재실행, 오류 처리
│   ├── MANIFEST.md               # Phase별 파일 역할 지도
│   ├── contracts/                # 무엇을 해야 하는가
│   ├── procedures/               # 어떻게 수행하는가
│   ├── schemas/                  # 산출물 형식
│   └── rubrics/                  # 평가 기준
│
├── .claude/
│   ├── settings.local.json       # Claude Code 권한과 로컬 설정
│   └── agents/                   # Claude Code sub-agent adapter
│
├── .agents/
│   └── skills/                   # Codex Skill adapter
│       ├── {harness-name}-orchestrator/
│       │   └── SKILL.md
│       └── {phase-skill}/
│           └── SKILL.md
│
├── .codex/
│   └── config.toml               # Codex 프로젝트 설정. 기본은 최소 설정
│
└── artifacts/                    # 실행 결과와 개선 기록
    ├── README.md
    ├── improvement-log.md
    └── {run-id}/
```

## 4. 각 폴더의 책임

| 위치 | 책임 | 넣으면 좋은 것 | 넣으면 안 되는 것 |
|---|---|---|---|
| `harness/contracts/` | 단계의 목적, 입력, 출력, 완료 기준, 금지사항 | 업무 의미, 성공 기준, 사람 승인 조건 | Claude/Codex 도구명, 모델명 |
| `harness/procedures/` | 수행 절차와 방법론 | 단계별 작업 순서, 조사·분석 방법 | 플랫폼 전용 호출 문법 |
| `harness/schemas/` | 산출물 형식 | 표, 파일 템플릿, 필수 섹션 | 판단 기준의 긴 설명 |
| `harness/rubrics/` | 평가 기준 | 점수표, 비교 기준, 통과 기준 | 특정 모델 선호 |
| `.claude/agents/` | Claude Code 실행 adapter | name, description, tools, model, 읽을 공통 파일 | 공통 업무 규칙의 긴 복사 |
| `.agents/skills/` | Codex 실행 adapter | name, description, 언제 쓰는지, 읽을 공통 파일 | 공통 업무 규칙의 긴 복사 |
| `.codex/config.toml` | Codex 프로젝트 설정 | 필요한 경우 모델·권한·sandbox override | 불필요한 전역 설정 복제 |
| `artifacts/` | 실행 기록 | 중간 산출물, 최종 산출물, 비교 리포트, 개선 기록 | 다음 실행에 필요 없는 임시 대화 |

## 5. 설계 카드

새 하네스를 만들기 전에 아래 항목을 채운다.
절반 이상 채워져 있으면 나머지는 `확인 필요`로 두고 청사진을 만들 수 있다.

| 항목 | 작성 내용 |
|---|---|
| 반복 업무 | 어떤 일을 반복해서 하네스로 만들 것인가? |
| 최종 산출물 | 마지막에 사용자가 실제로 열어보거나 의사결정에 쓰는 파일은 무엇인가? |
| 중간 산출물 | 최종 전에 어떤 표, 요약, 초안, 검토표가 필요한가? |
| 입력 자료 | 사용자가 먼저 줄 자료, 링크, 파일, 기준표는 무엇인가? |
| 먼저 물어볼 질문 | 누락되면 결과 품질이 크게 흔들리는 정보는 무엇인가? |
| 실패 처리 | 정보 부족, 도구 실패, 결과 충돌 시 어떻게 할 것인가? |
| 검증 기준 | 무엇을 만족해야 좋은 결과인가? |
| 사람 승인 지점 | 어떤 단계는 AI가 자동 확정하면 안 되는가? |
| 재실행 규칙 | 일부만 수정할 때 어느 Phase부터 다시 실행할 것인가? |
| 개선 기록 | 다음 실행을 위해 어떤 실패와 수정을 기록할 것인가? |

## 6. 하네스 7요소 체크

| 요소 | 확인 질문 | 산출물에 반영할 위치 |
|---|---|---|
| 목표 | 무엇을 만들면 성공인가? | `harness/ORCHESTRATOR.md`, contracts |
| 컨텍스트 | AI가 먼저 읽어야 할 자료는 무엇인가? | contracts, artifacts README |
| 도구 | 조사, 파일 작성, 브라우저, 계산 등 어떤 도구가 필요한가? | platform adapter |
| 중간 산출물 | 다음 단계가 반드시 읽어야 할 파일은 무엇인가? | schemas, MANIFEST |
| 검증 | 품질을 어떻게 판단할 것인가? | rubrics, contracts |
| 권한과 승인 | 사람 확인 전 자동 처리하면 안 되는 것은 무엇인가? | ORCHESTRATOR, contracts |
| 기록과 개선 | 실행 후 무엇을 남길 것인가? | artifacts README, improvement-log |

## 7. Phase 설계 원칙

각 Phase는 아래 네 가지가 명확해야 한다.

| 항목 | 설명 |
|---|---|
| 입력 | 이전 Phase 또는 사용자에게서 무엇을 읽는가 |
| 출력 | 어떤 파일을 어디에 저장하는가 |
| 완료 기준 | 다음 Phase로 넘어가기 위한 최소 조건 |
| 금지사항 | 이 Phase가 하면 안 되는 일 |

권장 Phase 수는 업무 규모에 따라 다르다.

- 작은 개인 업무: 3-5개 Phase
- 중간 규모 문서/리포트: 5-8개 Phase
- 가치투자 21단계 같은 큰 업무: 상위 21단계를 유지하되, 필요하면 내부 subphase를 둔다.

## 9. Procedure 템플릿

```md
# {Phase Name} 수행 절차

1. 입력 파일이 존재하는지 확인한다.
2. 필요한 공통 기준 또는 schema를 읽는다.
3. 핵심 작업을 수행한다.
4. 불확실한 정보와 확인된 정보를 분리한다.

6. `harness/schemas/{phase}.schema.md` 형식에 따라 산출물을 저장한다.
```

## 11. Claude Code Adapter 템플릿

name: {agent-name}

  - Read
  - Write
  - Glob

## 시작 전 필독

아래 파일을 순서대로 읽는다.

1. `harness/contracts/{phase}.contract.md`
2. `harness/procedures/{phase}.md`
3. `harness/schemas/{phase}.schema.md`
4. `artifacts/{run-id}/{previous-output}.md`

## 출력

`artifacts/{run-id}/{phase-output}.md`로 저장한다.

## Claude Code 전용 주의사항

- 플랫폼 도구 사용법만 적는다.
- 업무 규칙은 `harness/`를 단일 원본으로 따른다.
- 공통 업무 규칙을 이 파일에 길게 복사하지 않는다.

## 12. Codex Skill Adapter 템플릿

`.agents/skills/{skill-name}/SKILL.md`

```md
---
name: {skill-name}
description: "{한국어 요청 트리거와 사용 조건을 구체적으로 쓴다. 예: 분석, 재검토, 비교, 리포트 생성 요청에서 사용한다. 공통 contract/procedure를 따른다.}"
---

# {Skill Name}

Phase {n} {Role}의 Codex 어댑터다.

## 필수로 읽을 파일

아래 파일을 순서대로 읽는다.

1. `harness/contracts/{phase}.contract.md`
2. `harness/procedures/{phase}.md`
3. `harness/schemas/{phase}.schema.md`
4. `artifacts/{run-id}/{previous-output}.md`

## 실행 절차

1. 입력 산출물이 있는지 확인한다.
2. 공통 contract와 procedure를 그대로 따른다.
3. 결과를 schema에 맞게 저장한다.
4. 다음 Phase로 넘길 짧은 요약을 반환한다.

## Codex 어댑터 규칙

- `harness/contracts/{phase}.contract.md`와 `harness/procedures/{phase}.md`를 단일 원본으로 따른다.
- 이 Skill에는 공통 업무 규칙을 길게 복사하지 않는다.
- 이 Phase Skill에서 `.claude/`를 수정하지 않는다.

## 출력

작성 파일:

- `artifacts/{run-id}/{phase-output}.md`
```

## 13. Orchestrator 템플릿

`harness/ORCHESTRATOR.md`

````md
# {Harness Name} Orchestrator

## 역할
전체 실행 흐름을 관리한다.
모드 선택 → 입력 수집 → 분석 → 생성 → 검토 → 최종 산출 → 개선 기록 순서로 진행한다.

각 단계에서 해당 contract와 procedure를 읽고 수행한다.

## 수정 경계

- 업무 의미는 `harness/contracts/`에서 변경한다.
- 수행 절차는 `harness/procedures/`에서 변경한다.
- 출력 형식은 `harness/schemas/`에서 변경한다.
- 평가 기준은 `harness/rubrics/`에서 변경한다.
- Claude 실행 방식은 `.claude/agents/`에서 변경한다.
- Codex 실행 방식은 `.agents/skills/`와 `.codex/`에서 변경한다.

## 시작 전 확인

`artifacts/`를 확인해 초기 실행, 부분 재실행, 비교 모드 중 하나로 분기한다.

## Phase 0: 실행 모드 선택

- Claude Code 단일 실행
- Codex 단일 실행
- 둘 다 실행 후 비교

## Phase 1..N

각 Phase마다 아래를 쓴다.

```text
목표:
입력:
출력:
완료 조건:
실패 시:
사람 승인 필요:
```

## 부분 재실행 규칙

| 사용자 요청 | 재실행 Phase |
|---|---|
| "{부분}만 바꿔줘" | 해당 Phase부터 최종 Phase까지 |

## 오류 처리

| 상황 | 대응 |
|---|---|
| 입력 부족 | 질문 후 대기 또는 명시적 가정 |
| 조사 실패 | 확인 필요 표시 |
| 계산 불일치 | 계산 Phase 재실행 |
| 검토 실패 | 수정 목록 작성 후 해당 Phase 재실행 |
```
````

│   └── final.md

## 18. 가치투자 21단계 하네스에 적용할 때

가치투자 하네스는 여행 계획보다 훨씬 두꺼운 하네스가 필요하다.
이유는 결과가 실제 투자 판단, 금전 손실, 심리적 확신, 리스크 관리에 영향을 줄 수 있기 때문이다.

권장 원칙:

- AI는 투자 결정을 자동 확정하지 않는다.
- 모든 결론은 근거, 반대 근거, 불확실성, 확인 필요 항목을 분리한다.
- 원자료와 계산 산출물을 파일로 남긴다.
- valuation, risk, red-team, final memo는 분리한다.
- 최종 매수/매도/보유 판단은 사람 승인 지점으로 둔다.

예상 상위 구조:

```text
value-investing-harness/
├── harness/
│   ├── ORCHESTRATOR.md
│   ├── MANIFEST.md
│   ├── contracts/
│   │   ├── 01-intake.contract.md
│   │   ├── 02-source-collection.contract.md
│   │   ├── ...
│   │   └── 21-final-decision-memo.contract.md
│   ├── procedures/
│   ├── schemas/
│   └── rubrics/
├── .claude/agents/
├── .agents/skills/
├── .codex/config.toml
└── artifacts/
```

가치투자 하네스에서 특히 두껍게 잡을 부분:

| 영역 | 이유 | 권장 산출물 |
|---|---|---|
| 자료 수집 | 출처 품질이 결론을 좌우함 | source inventory, source quality table |
| 사실 레이어 | 사실과 해석이 섞이면 위험함 | fact layer |
| 재무 계산 | 계산 오류가 직접 판단을 왜곡함 | financial model, assumption table |
| 밸류에이션 | 가정 민감도가 큼 | valuation scenario table |
| 리스크 | 낙관 편향 방지 | risk register |
| 반대 논리 | 확증 편향 방지 | red-team memo |
| 최종 메모 | 사람이 승인할 판단 자료 | final investment memo |

## 20. 언제 템플릿만으로 충분하고, 언제 대화가 필요한가

템플릿만으로 충분한 경우:

- 업무 흐름이 이미 대략 정해져 있다.
- 최종 산출물이 분명하다.
- 각 단계의 입력과 출력이 어느 정도 보인다.
- 실패해도 큰 위험이 없다.

추가 대화가 필요한 경우:

- 단계가 많고 서로 의존성이 복잡하다.
- 돈, 법률, 개인정보, 외부 제출처럼 책임이 크다.
- 평가 기준이 아직 모호하다.
- 사람 승인 지점이 불명확하다.
- 어떤 자료를 신뢰할지 정해야 한다.

가치투자 21단계 하네스는 템플릿만으로 바로 완성하기보다, 이 템플릿으로 1차 청사진을 빠르게 만들고, 이후 단계별로 몇 차례 조정하는 방식이 가장 좋다.

즉, 템플릿은 질문답변을 없애는 도구가 아니라 질문답변의 양을 줄이고, 같은 구조 설명을 반복하지 않게 만드는 도구다.
