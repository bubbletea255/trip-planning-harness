# 공용 하네스 템플릿 체크리스트 v2

이 문서는 반복 업무를 Claude Code와 Codex 양쪽에서 실행할 수 있는 하네스로 만들기 위한 공용 설계 템플릿이다.

v1의 핵심은 `harness/` 공통 원장과 플랫폼별 adapter를 분리하는 것이었다.
v2의 핵심은 여기에 더해 **최소 형식 충족이 아니라 고품질 산출물까지 강제하는 계약**을 넣는 것이다.

이 템플릿은 특정 분야 전용이 아니다.
여행 계획, 리포트 작성, 문서 검토, 투자 분석, 기업 조사, 의사결정 메모처럼 반복 가능한 지식 작업에 사용할 수 있다.
다만 앞으로 가치투자 21단계 하네스에 집중적으로 재사용할 것을 고려해, 기본값은 짧은 요약이 아니라 **근거가 남고, 반대 관점이 검토되며, 사람이 최종 판단할 수 있는 분석형 산출물**로 둔다.

---

## 1. v2의 문제의식

AI 모델은 생각보다 지침 구조를 잘 따라간다.
따라서 결과물 차이는 모델 지능 차이만이 아니라, 아래 요소에서 크게 발생한다.

- 무엇을 좋은 결과로 정의했는가
- 어느 정도 깊이까지 분석하라고 했는가
- 중간 산출물의 중요한 정보를 최종 산출물에 보존하라고 했는가
- 불확실성, 대안, 반대 근거, 체크리스트를 강제했는가
- 평가 루브릭이 실제 사용자가 느끼는 품질을 잡아내는가

나쁜 하네스는 "파일이 만들어졌는가"만 본다.
좋은 하네스는 "그 파일이 실제 의사결정, 실행, 검토, 승인에 쓸 수 있는가"까지 본다.

---

## 2. 핵심 원칙

> 업무 의미는 `harness/`에 두고, 플랫폼별 실행 방식은 얇은 adapter로 둔다.

> 최종 산출물은 최소 형식만 만족해서는 완료로 보지 않는다. 사용자가 실제로 판단하거나 실행할 수 있을 만큼 충분해야 한다.

> 모델의 자율성에 맡기지 말고, 좋은 결과의 구조를 contract, procedure, schema, rubric에 명시한다.

---

## 3. 이 템플릿을 쓰는 상황

이 템플릿은 아래 상황에서 사용한다.

- 반복 업무를 AI에게 맡기고 싶다.
- 중간 산출물과 최종 산출물을 파일로 남기고 싶다.
- Claude Code와 Codex 중 선택해서 같은 하네스를 실행하고 싶다.
- 두 모델의 결과를 비교하고 교차검증하고 싶다.
- 특정 업무를 한 번 잘 만든 뒤 다음 업무에 재사용하고 싶다.
- 최종 결과가 단순 요약이 아니라 분석, 의사결정, 실행, 승인에 쓰여야 한다.

사용하지 않는 것이 좋은 경우:

- 한 번만 할 단순 질문
- 결과 파일이 필요 없는 짧은 대화
- 구조보다 즉흥적 아이디어 탐색이 중요한 작업

## 4. 권장 폴더 구조

```text
{harness-project}/
├── AGENTS.md                     # Codex와 공통 프로젝트 안내
├── CLAUDE.md                     # Claude Code 프로젝트 안내
│
├── harness/                      # 공통 업무 원장
│   ├── ORCHESTRATOR.md           # 전체 실행 흐름, Phase, 재실행, 오류 처리
│   ├── MANIFEST.md               # Phase별 파일 역할 지도
│   ├── contracts/                # 무엇을 해야 하는가
│   ├── procedures/               # 어떻게 수행하는가
│   ├── schemas/                  # 산출물 형식과 정보 밀도
│   └── rubrics/                  # 평가 기준과 품질 판정
│
├── .claude/
│   ├── settings.local.json       # Claude Code 권한과 로컬 설정
│   └── agents/                   # Claude Code 실행 adapter
│
├── .agents/
│   └── skills/                   # Codex Skill adapter
│       ├── {harness-name}-orchestrator/
│       │   └── SKILL.md
│       └── {phase-skill}/
│           └── SKILL.md
│
├── .codex/
│   └── config.toml               # Codex 프로젝트 설정. 기본은 최소 설정
│
└── artifacts/                    # 실행 결과와 개선 기록
    ├── README.md
    ├── improvement-log.md
    ├── {run-id}/
    └── comparison-{run-id}.md
```

## 5. 각 파일군의 책임

| 위치 | 책임 | 넣으면 좋은 것 | 넣으면 안 되는 것 |
|---|---|---|---|
| `harness/contracts/` | 단계의 목적, 입력, 출력, 완료 기준, 금지사항 | 업무 의미, 성공 기준, 품질 기준, 사람 승인 조건 | Claude/Codex 도구명, 모델명 |
| `harness/procedures/` | 수행 절차와 방법론 | 단계별 작업 순서, 분석 방법, 자체 점검, 실패 처리 | 플랫폼 전용 호출 문법 |
| `harness/schemas/` | 산출물 형식과 정보 밀도 | 필수 섹션, 표, 상세 수준, 보존해야 할 정보 | 긴 판단 철학 |
| `harness/rubrics/` | 평가 기준 | 점수표, 비교 기준, 통과 기준, 우수 기준 | 특정 모델 선호 |
| `.claude/agents/` | Claude Code adapter | name, description, tools, 읽을 공통 파일 | 공통 업무 규칙의 긴 복사 |
| `.agents/skills/` | Codex adapter | name, description, 트리거, 읽을 공통 파일 | 공통 업무 규칙의 긴 복사 |
| `.codex/config.toml` | Codex 프로젝트 설정 | 필요한 최소 설정 | 불필요한 전역 설정 복제 |
| `artifacts/` | 실행 기록 | 중간 산출물, 최종 산출물, 비교 리포트, 개선 기록 | 다음 실행에 필요 없는 임시 대화 |

## 6. 설계 카드 v2

새 하네스를 만들기 전에 아래 항목을 채운다.
비어 있는 항목은 억지로 추측하지 말고 `확인 필요`로 둔다.

| 항목 | 작성 내용 |
|---|---|
| 반복 업무 | 어떤 일을 반복해서 하네스로 만들 것인가? |
| 최종 사용자 | 이 결과를 누가 읽고 어떤 결정을 하는가? |
| 최종 산출물 | 마지막에 사용자가 실제로 열어보거나 판단에 쓰는 파일은 무엇인가? |
| 산출물 깊이 | 빠른 요약, 표준 리포트, 의사결정급 산출물 중 무엇인가? |
| 중간 산출물 | 최종 전에 어떤 표, 요약, 계산, 검토표가 필요한가? |
| 입력 자료 | 사용자가 먼저 줄 자료, 링크, 파일, 기준표는 무엇인가? |
| 먼저 물어볼 질문 | 누락되면 결과 품질이 크게 흔들리는 정보는 무엇인가? |
| 핵심 판단 | 이 업무에서 AI가 판단해야 하는 핵심 쟁점은 무엇인가? |
| 금지할 추측 | 틀리면 위험한 가정, 숫자, 결론은 무엇인가? |
| 불확실성 처리 | 확인된 사실, 추정, 확인 필요를 어떻게 분리할 것인가? |
| 반대 관점 | 어떤 반론, 대안, 실패 시나리오를 반드시 검토해야 하는가? |
| 검증 기준 | 무엇을 만족해야 좋은 결과인가? |
| 사람 승인 지점 | 어떤 단계는 AI가 자동 확정하면 안 되는가? |
| 재실행 규칙 | 일부만 수정할 때 어느 Phase부터 다시 실행할 것인가? |
| 개선 기록 | 다음 실행을 위해 어떤 실패와 수정을 기록할 것인가? |

## 7. 산출물 깊이 단계

하네스는 산출물 깊이를 명시해야 한다.
명시하지 않으면 기본값은 `표준 리포트`로 둔다.
가치투자, 리스크 분석, 장기 의사결정은 기본값을 `의사결정급 산출물`로 둔다.

| 단계 | 사용 상황 | 요구 수준 |
|---|---|---|
| 빠른 요약 | 빠른 방향 확인, 초안, 브레인스토밍 | 핵심 결론, 주요 근거, 다음 질문 |
| 표준 리포트 | 일반 업무 산출물, 실행 계획, 비교 검토 | 요약, 상세 근거, 항목별 내역, 대안, 체크리스트 |
| 의사결정급 산출물 | 투자, 법무, 재무, 전략, 고위험 판단 | 근거 추적성, 계산표, 가정, 민감도, 반대 근거, 리스크, 사람 승인 지점 |

---

## 8. 산출물 품질 계약

각 최종 산출물은 최소 형식만 만족해서는 완료로 보지 않는다.
사용자가 실제 의사결정, 실행, 검토, 승인에 사용할 수 있어야 한다.

최종 산출물 schema에는 업무 성격에 맞게 아래 요소를 포함한다.
모든 업무에 전부 넣을 필요는 없지만, 제외한 항목은 제외 이유가 분명해야 한다.

| 요소 | 의미 | 산출물에 드러나는 형태 |
|---|---|---|
| 핵심 요약 | 가장 중요한 결론과 판단 | Executive summary, 핵심 결론, 추천안 |
| 상세 근거 | 결론을 뒷받침하는 사실, 계산, 출처 | 근거 표, 출처 링크, 계산 근거 |
| 항목별 내역 | 큰 숫자나 결론을 구성하는 세부 항목 | 카테고리별 표, 항목별 상세표 |
| 가정 | 결론이 의존하는 전제 | assumption table, 가정 목록 |
| 불확실성 | 확인된 사실과 추정의 분리 | 확인됨, 추정, 확인 필요 |
| 대안/시나리오 | 주요 가정이 틀렸을 때의 선택지 | base/bull/bear, Plan A/B/C |
| 반대 관점 | 결론에 불리한 근거 | red-team, counterargument |
| 리스크/주의사항 | 실행 전 알아야 할 위험 | risk register, 주의사항 |
| 실행 체크리스트 | 사용자가 다음 행동으로 옮기는 목록 | 우선순위별 체크리스트 |
| 승인 지점 | AI가 자동 확정하지 않을 부분 | 사람 승인 필요, 최종 판단 보류 |

## 9. 최소 완료 기준과 우수 산출물 기준 분리

각 Phase의 contract에는 최소 완료 기준과 우수 산출물 기준을 분리한다.

```md
## 최소 완료 기준
- 필수 입력을 읽었다.
- 필수 출력 파일을 만들었다.
- 필수 섹션이 빠지지 않았다.

## 우수 산출물 기준
- 사용자가 실제 판단 또는 실행에 사용할 수 있을 만큼 상세하다.
- 결론, 근거, 가정, 불확실성, 대안이 분리되어 있다.
- 큰 숫자나 중요한 판단은 항목별 내역으로 풀려 있다.
- 다음 단계가 읽어야 할 핵심 정보가 누락되지 않았다.
- 사람 승인 또는 추가 확인이 필요한 지점이 명시되어 있다.
```

최소 완료 기준은 다음 Phase로 넘어갈 수 있는 기준이다.
우수 산출물 기준은 모델 간 비교와 품질 개선의 기준이다.

## 10. 좋은 Schema의 조건

Schema는 단순한 목차가 아니다.
Schema는 "결과물이 어느 정도 깊이와 형태를 가져야 하는가"를 정하는 정보 구조 계약이다.

좋은 schema는 아래를 포함한다.

- 필수 섹션
- 각 섹션이 담아야 할 정보
- 표가 필요한 경우 컬럼명
- 요약과 상세의 분리
- 확인된 정보와 추정 정보의 표시 방식
- 이전 Phase에서 반드시 보존해야 할 정보
- 누락되면 안 되는 주의사항
- 모바일 또는 문서 가독성 같은 사용성 기준

나쁜 schema는 아래처럼 너무 느슨하다.

```md
## 필수 섹션
1. 개요
2. 분석
3. 결론
```

좋은 schema는 아래처럼 구체적이다.

```md
## 필수 섹션
1. 핵심 요약
   - 최종 판단
   - 판단을 바꿀 수 있는 핵심 변수
   - 사람 승인 필요 여부

2. 근거 표
   - 항목
   - 확인된 사실
   - 출처
   - 신뢰도
   - 확인 필요

3. 상세 분석
   - 결론을 만든 주요 계산 또는 논리
   - 긍정 근거
   - 부정 근거
   - 불확실성

4. 대안과 시나리오
   - 기본 시나리오
   - 낙관 시나리오
   - 비관 시나리오
   - 각 시나리오에서 달라지는 판단

5. 실행 체크리스트
   - 최우선
   - 추가 확인
   - 후속 실행
   - 사람 승인
```

## 11. 중간 산출물 보존 규칙

최종 산출물 단계는 이전 Phase의 중요한 정보를 버리면 안 된다.

Report, Memo, Dashboard, Final Recommendation 같은 최종 Phase procedure에는 아래 점검을 넣는다.

```md
## 이전 산출물 보존 점검

최종 산출물을 저장하기 전에 이전 Phase 산출물을 다시 확인한다.

- 핵심 결론이 최종 산출물에 반영됐는가?
- 중요한 숫자와 계산 근거가 보존됐는가?
- 출처와 확인 필요 항목이 빠지지 않았는가?
- 주의사항과 리스크가 요약 과정에서 사라지지 않았는가?
- 대안과 실패 시나리오가 충분히 남아 있는가?
- 체크리스트가 사용자가 행동할 수 있는 형태인가?
```

요약은 허용된다.
하지만 핵심 근거, 위험, 확인 필요, 사람 승인 지점은 요약 과정에서 삭제하면 안 된다.

## 12. 하네스 7요소 체크

| 요소 | 확인 질문 | 산출물에 반영할 위치 |
|---|---|---|
| 목표 | 무엇을 만들면 성공인가? | `harness/ORCHESTRATOR.md`, contracts |
| 컨텍스트 | AI가 먼저 읽어야 할 자료는 무엇인가? | contracts, artifacts README |
| 도구 | 조사, 파일 작성, 계산, 브라우저 등 어떤 도구가 필요한가? | platform adapter |
| 중간 산출물 | 다음 단계가 반드시 읽어야 할 파일은 무엇인가? | schemas, MANIFEST |
| 검증 | 품질을 어떻게 판단할 것인가? | rubrics, contracts |
| 권한과 승인 | 사람 확인 전 자동 처리하면 안 되는 것은 무엇인가? | ORCHESTRATOR, contracts |
| 기록과 개선 | 실행 후 무엇을 남길 것인가? | artifacts README, improvement-log |

## 13. Phase 설계 원칙

Phase는 많을수록 좋은 것이 아니다.
중간 판단이 독립적으로 검토되어야 하거나, 다음 단계가 읽을 파일이 분명할 때 나눈다.

각 하네스의 Phase는 아래 예시 흐름을 그대로 복사해서 만들지 않는다.
Phase는 해당 하네스의 목표, 입력 자료, 판단 단위, 중간 산출물, 검증 방식에 맞게 새로 설계한다.

특히 가치투자처럼 여러 개의 전문 하네스로 나뉘는 구조에서는 각 하네스마다 고유한 Phase가 필요하다.
예를 들어 밸류에이션 하네스, 밸류체인 하네스, Market 하네스, Management 하네스는 서로 다른 질문과 산출물을 가지므로 같은 Phase 구조를 강제로 공유하지 않는다.

각 Phase는 아래를 가져야 한다.

| 항목 | 의미 |
|---|---|
| 목적 | 이 Phase가 왜 필요한가 |
| 입력 | 이전 Phase 또는 사용자에게서 무엇을 읽는가 |
| 출력 | 어떤 파일을 어디에 저장하는가 |
| 최소 완료 기준 | 다음 Phase로 넘어가기 위한 조건 |
| 우수 산출물 기준 | 좋은 결과로 평가되기 위한 조건 |
| 금지사항 | 이 Phase가 하면 안 되는 일 |
| 실패 처리 | 정보 부족, 도구 실패, 충돌을 어떻게 남기는가 |

Phase 설계 예시:

- 밸류에이션 하네스는 재무 정규화, 핵심 가정 설정, 시나리오 구성, DCF, 멀티플, 민감도, 검증, 최종 메모 같은 Phase가 필요할 수 있다.
- 밸류체인 하네스는 산업 구조, 공급자, 고객, 유통, 경쟁 구도, 병목, 협상력, 리스크 같은 Phase가 필요할 수 있다.
- Management 하네스는 경영진 이력, 자본배분, 주주친화성, 인센티브, 과거 발언 검증, 평판 리스크 같은 Phase가 필요할 수 있다.

아래 목록은 고정 순서가 아니다.
각 하네스의 목적에 맞게 선택, 병합, 삭제, 재배열하는 **Phase 역할 후보 목록**이다.

| 역할 후보 | 의미 |
|---|---|
| 입력 정리 | 사용자 입력, 범위, 대상, 제약 조건을 확정한다 |
| 자료 수집 | 필요한 원자료, 출처, 데이터, 문서를 모은다 |
| 자료 품질 평가 | 출처 신뢰도, 최신성, 누락, 편향을 확인한다 |
| 사실 레이어 구성 | 확인된 사실과 해석을 분리한다 |
| 분석 | 해당 하네스의 핵심 계산, 비교, 판단을 수행한다 |
| 시나리오/대안 | 주요 가정이 달라질 때 결과가 어떻게 바뀌는지 본다 |
| 반대 관점 검토 | 결론에 불리한 근거와 실패 가능성을 검토한다 |
| 최종 산출물 작성 | 사용자가 판단하거나 실행할 수 있는 문서로 통합한다 |
| 검증 | 계산 오류, 논리 비약, 누락, 모순을 점검한다 |
| 개선 기록 | 다음 실행을 위해 문제와 개선점을 남긴다 |

LLM은 위 목록을 그대로 복사하지 말고, 새 하네스의 목적에 맞는 Phase 구조를 먼저 제안해야 한다.
사용자가 이미 특정 업무 절차나 단계명을 제시했다면 그 구조를 우선한다.
단, 입력 정리, 중간 산출물, 최종 산출물, 검증, 개선 기록의 책임은 가능한 한 어떤 방식으로든 포함한다.

## 14. Contract 템플릿 v2

```md
# {Phase Name} Contract

## 목적
이 Phase가 달성해야 하는 일을 한 문단으로 쓴다.

## 활성화 조건
- 언제 이 Phase를 실행하는가
- 어떤 이전 산출물이 있어야 하는가

## 입력
- `artifacts/{run-id}/...`
- 사용자 입력 또는 참고 자료

## 출력
- `artifacts/{run-id}/...`

## 최소 완료 기준
- 필수 입력을 읽었다.
- 필수 출력 파일을 저장했다.
- schema의 필수 섹션이 빠지지 않았다.

## 우수 산출물 기준
- 사용자가 실제 판단 또는 실행에 사용할 수 있을 만큼 상세하다.
- 결론, 근거, 가정, 불확실성, 대안이 분리되어 있다.
- 중요한 숫자와 판단은 항목별 내역으로 풀었다.
- 확인 필요와 사람 승인 지점을 명시했다.

## 금지사항
- 확인되지 않은 정보를 확정 사실처럼 쓰지 않는다.
- 중요한 가정이나 리스크를 숨기지 않는다.
- 다음 Phase가 필요한 핵심 정보를 생략하지 않는다.
- 플랫폼별 도구명이나 모델명을 업무 규칙으로 넣지 않는다.

## 실패 처리
- 자료가 부족하면 `확인 필요`로 남긴다.
- 도구가 실패하면 실패 사실과 영향 범위를 기록한다.
- 결론을 낼 수 없으면 억지 결론 대신 판단 보류 조건을 쓴다.

## 사람 승인 필요
- AI가 자동 확정하면 안 되는 결정 또는 실행 지점을 쓴다.

## 수행 방법
`harness/procedures/{phase}.md`를 읽고 따른다.
```

- 불확실한 내용을 확정적으로 쓰지 않았는가?
- 반대 근거 또는 실패 가능성을 검토했는가?
- 사용자가 다음 행동을 알 수 있는가?

## 17. Rubric 템플릿 v2

루브릭은 업무 정답만 평가하면 안 된다.
최종 산출물의 사용성과 분석 품질도 평가해야 한다.

```md
# {Harness Name} Judge Rubric

모든 항목은 1-5점 척도이며, 가중치를 적용해 100점 만점으로 환산한다.

## 평가 항목

| 항목 | 가중치 | 평가 질문 |
|---|---:|---|
| 업무 완결성 | 20% | 요청한 범위와 필수 산출물이 모두 충족됐는가? |
| 근거 추적성 | 15% | 결론이 입력 자료, 출처, 계산과 연결되는가? |
| 분석 깊이 | 15% | 표면적 요약이 아니라 원인, 구조, 숫자, 의미를 분석했는가? |
| 불확실성 분리 | 10% | 확인된 사실, 추정, 확인 필요가 구분됐는가? |
| 대안/반대 관점 | 10% | 대안, 실패 시나리오, 반대 근거를 검토했는가? |
| 실행 가능성 | 10% | 사용자가 다음 행동을 알 수 있는가? |
| 최종 산출물 사용성 | 10% | 최종 파일이 실제 검토, 실행, 승인에 쓰기 좋은가? |
| 체크리스트 품질 | 5% | 체크리스트가 우선순위별, 상황별로 정리됐는가? |
| 사람 승인 안전성 | 5% | AI가 자동 확정하면 안 되는 지점을 남겼는가? |

## 점수 기준 예시

5점: 사용자가 바로 의사결정 또는 실행에 활용할 수 있다.
4점: 대부분 충분하나 일부 상세 또는 검증이 부족하다.
3점: 기본 구조는 있으나 중요한 근거, 대안, 확인 필요가 부족하다.
2점: 형식은 있지만 실제 사용하기 어렵다.
1점: 필수 정보가 빠졌거나 판단을 왜곡할 수 있다.
```

도메인별 루브릭은 이 공용 루브릭을 바탕으로 조정한다.
예를 들어 가치투자 하네스는 `재무 계산 정확성`, `밸류에이션 민감도`, `리스크 식별`, `원자료 품질`의 가중치를 높인다.

## 20. Orchestrator 설계 원칙

Orchestrator는 전체 실행 흐름의 입구다.
사용자의 자연어 요청을 Phase 실행으로 연결한다.

반드시 포함할 것:

- 새 실행, 재실행, 부분 수정, 비교 모드 구분
- run-id 생성 규칙
- 기존 산출물 덮어쓰기 금지
- Phase별 입력/출력 의존 관계
- 실패 시 중단 기준
- 사람 승인 지점
- 최종 산출물 품질 점검
- 개선 기록 작성

Orchestrator가 직접 모든 일을 하도록 만들지 않는다.
Orchestrator는 흐름과 전달물을 관리하고, 각 Phase의 업무 규칙은 contract/procedure/schema에 둔다.

---

## 21. 최종 산출물 단계 특별 규칙

최종 리포트, 최종 메모, 최종 HTML, 최종 대시보드, 최종 추천안 단계에는 아래 규칙을 강하게 넣는다.

```md
## 최종 산출물 특별 규칙

이 Phase는 이전 산출물을 단순히 짧게 요약하는 단계가 아니다.
사용자가 실제 판단, 실행, 승인에 사용할 수 있는 최종 문서를 만드는 단계다.

반드시 포함한다.

- 핵심 요약
- 상세 근거
- 항목별 내역
- 중요한 숫자의 계산 근거
- 불확실성 및 확인 필요
- 리스크와 주의사항
- 대안 또는 시나리오
- 실행 체크리스트
- 사람 승인 필요 항목

이전 Phase에 존재하던 중요한 정보가 최종 산출물에서 사라지면 안 된다.
```

이 규칙은 특정 도메인 항목이 아니다.
여행, 투자, 문서 검토, 전략 보고서 등 대부분의 실행형 산출물에 적용할 수 있다.

## 23. 개선 기록 규칙

하네스는 한 번 만들고 끝나는 것이 아니다.
실행 후 발견한 문제를 `artifacts/improvement-log.md`에 남긴다.

기록할 것:

- 모델 차이로 보였지만 실제로는 지침 차이였던 부분
- schema가 너무 느슨해 결과물이 빈약했던 부분
- rubric이 사용자 체감 품질을 잡지 못한 부분
- 특정 Phase가 이전 산출물의 핵심 정보를 잃어버린 부분
- 확인 필요와 확정 사실이 섞인 부분
- 사람 승인 없이 자동 확정하면 위험했던 부분

기록 형식:

```md
## YYYY-MM-DD | {run-id} | {개선 유형}

**발견된 문제**:
**원인**:
**적용할 개선**:
**수정 위치**:
**다음 실행에서 확인할 점**:
```

## 24. 가치투자 하네스에 적용할 때의 기본 원칙

가치투자 하네스는 기본적으로 `의사결정급 산출물`이다.
따라서 아래 원칙을 기본값으로 둔다.

- AI는 투자 결정을 자동 확정하지 않는다.
- 최종 매수, 매도, 보유 판단은 사람 승인 지점으로 둔다.
- 모든 결론은 근거, 반대 근거, 불확실성, 확인 필요 항목을 분리한다.
- 원자료와 계산 산출물을 파일로 남긴다.
- 재무 계산, 밸류에이션, 리스크, red-team, final memo는 분리한다.
- 숫자는 총액만 쓰지 않고 구성 항목과 가정을 함께 남긴다.
- 투자 thesis와 anti-thesis를 함께 작성한다.
- base, bull, bear 시나리오와 판단 변화 조건을 남긴다.
- 최종 메모에는 "무엇을 더 확인하면 판단이 바뀌는가"를 반드시 포함한다.

가치투자 하네스에서 특히 두껍게 잡을 부분:

| 영역 | 이유 | 권장 산출물 |
|---|---|---|
| 자료 수집 | 출처 품질이 결론을 좌우함 | source inventory, source quality table |
| 사실 레이어 | 사실과 해석이 섞이면 위험함 | fact layer |
| 재무 계산 | 계산 오류가 직접 판단을 왜곡함 | financial model, assumption table |
| 밸류에이션 | 가정 민감도가 큼 | valuation scenario table |
| 리스크 | 좋은 이야기만 보면 위험함 | risk register, red-team memo |
| 최종 판단 | 자동 확정하면 안 됨 | decision memo, approval gate |

## 26. 수정 경계

| 바꾸고 싶은 것 | 수정 위치 |
|---|---|
| 업무 의미 | `harness/contracts/` |
| 수행 절차 | `harness/procedures/` |
| 출력 형식과 정보 밀도 | `harness/schemas/` |
| 평가 기준과 품질 루브릭 | `harness/rubrics/` |
| 전체 흐름 | `harness/ORCHESTRATOR.md` |
| 파일 역할 지도 | `harness/MANIFEST.md` |
| Claude 실행 방식 | `.claude/agents/` |
| Codex 실행 방식 | `.agents/skills/`, `.codex/` |
| 실행 결과와 회고 | `artifacts/` |
| 프로젝트 공통 안내 | `AGENTS.md`, `CLAUDE.md` |

중요:

- 공통 업무 규칙은 adapter에 길게 복사하지 않는다.
- 플랫폼별 adapter는 얇게 유지한다.
- 결과 차이가 생기면 먼저 contract/procedure/schema/rubric이 충분히 구체적인지 확인한다.
- 모델 차이로 결론 내리기 전에 지침 차이, schema 느슨함, rubric 누락을 먼저 점검한다.

## 27. 최종 체크리스트

새 하네스 청사진 또는 파일 구성을 마치기 전에 확인한다.

- [ ] 최종 산출물이 무엇인지 분명하다.
- [ ] 산출물 깊이가 정해져 있다.
- [ ] 최소 완료 기준과 우수 산출물 기준이 분리되어 있다.
- [ ] schema가 단순 목차가 아니라 정보 밀도까지 지정한다.
- [ ] procedure가 이전 산출물 보존 점검을 포함한다.
- [ ] rubric이 실제 사용자 체감 품질을 평가한다.
- [ ] 불확실성, 대안, 반대 관점, 사람 승인 지점이 빠지지 않았다.
- [ ] Claude/Codex adapter가 공통 원장을 참조하는 얇은 구조다.
- [ ] 실행 결과와 개선 기록이 `artifacts/`에 남는다.
- [ ] 다음 하네스 생성자가 이 문서만 읽고도 같은 구조를 재현할 수 있다.
